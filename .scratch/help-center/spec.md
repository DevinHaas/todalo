# Help center

Status: ready-for-agent (decisions agreed 2026-11-11)

## Problem Statement

Someone using Todalo who gets stuck has nowhere to look. There is no help
site, no how-to pages and no reference. The only help entry in the app, "Help
& resources", opens the keyboard-shortcut sheet. Features that are new to most
people (Seasons, Rituals, the Coach, Ramble, Horizons, filter queries) are
explained only by short in-app strings, and one in-app string already promises
a help link that does not exist. The only contact route is a personal email
address on the privacy and terms pages.

## Solution

A public help center at `help.todalo.app`, modelled on the Todoist Help Center:
a landing page with search and illustrated category cards, category pages that
list their articles, and text-first articles with numbered steps, callouts and
cropped screenshots. It documents the new client on web and Mac, with iOS added
when it ships. Illustrations share one house style derived from the bonsai mark
and are generated with Higgsfield. The app links to the help center from "Help
& resources".

## User Stories

### Finding help

1. As a Todalo user, I want a help site at a memorable address, so that I know where to go when I am stuck.
2. As a Todalo user, I want a search box on the help landing page, so that I can find an answer without browsing.
3. As a Todalo user, I want suggested searches under the search box, so that I can reach common answers in one click.
4. As a Todalo user, I want search available from every page, so that I can look something else up without going back to the landing page.
5. As a Todalo user, I want search results to show the article's category and a text excerpt, so that I can pick the right result.
6. As a Todalo user, I want a clear message when a search finds nothing, with a route to support, so that I am not left at a dead end.
7. As a Todalo user, I want illustrated category cards on the landing page, so that I can recognise the area I need at a glance.
8. As a Todalo user, I want each category page to list all its articles on one page, so that I can scan what is covered.
9. As a Todalo user, I want breadcrumbs on every article, so that I can move back up to the category or the landing page.
10. As a Todalo user, I want related articles listed beside an article, so that I can continue to the next relevant topic.
11. As a Todalo user, I want to open the help center from "Help & resources" in the app, so that I do not have to remember the address.
12. As a Todalo user, I want the keyboard-shortcut sheet to remain reachable in the app, so that I do not lose the quick reference I already use.
13. As a person evaluating Todalo, I want the help center to be readable without an account, so that I can judge the product before signing up.
14. As a person searching the web, I want help articles to appear in search engines with a sensible title and description, so that I can land directly on the answer.
15. As a person sharing an article link, I want a branded preview image, so that the link looks trustworthy in chat and social apps.

## Implementation Decisions

### Scope and audience

- The help center documents the new client only (the shared Tauri client, ADR 0008). The legacy Next application is not documented.
- Platforms at launch are Web and Mac. iOS is added as a third platform when the iOS app ships; the platform model must accept it without restructuring articles.
- English only. The product is written "Todalo" (capitalised) throughout the help center, even though the app chrome writes it lowercase.
- Glossary terms follow the project's domain glossary: Season, Ritual, Goal, Milestone, Horizon, Coach, Ramble, Pattern.

### Application and deployment

- A new docs application in the monorepo, picked up by the existing workspace and build pipeline. It is a Next application using Fumadocs (MIT) with MDX content stored in the repository.
- It is deployed as its own Coolify service, separate from the marketing site and the API, and served at `help.todalo.app`. It needs no database and no authentication.
- It does not import from the client or the marketing application. The brand fonts (the display face used on the landing page for headings, Geist for body) and the colour tokens are copied into the docs application. No shared UI package is extracted.
- It has its own slim footer: Todalo home, privacy, terms, support address.
- Fumadocs support for the repository's Next version must be confirmed before scaffolding. If it is not supported, the fallback is hand-rolled MDX pages with a static search index; the content model below does not change.

### Information architecture

- Three levels: landing, category, article. No sub-categories; a category page may group its articles under headings.
- Seven categories in this order: Get started; Tasks & capture; Organise & views; Goals, seasons & rituals; Coach; Integrations; Apps & account.
- Article addresses are `/{category}/{article}` with readable slugs and no generated ID suffix.
- 37 articles in v1:
  - **Get started:** Get started with Todalo; Use Todalo on the web or install it on your Mac; Create your account and sign in; Bring your tasks from Todoist; Todalo glossary.
  - **Tasks & capture:** Introduction to tasks; Use Quick Add; Schedule a date and time; Introduction to recurring dates; Set a priority; Use sub-tasks; Add comments and files to tasks; Add or manage multiple tasks; Dictate tasks with Ramble.
  - **Organise & views:** Use the Inbox; Introduction to projects and sections; Introduction to labels; Introduction to filters; Plan your day with the Today view; Plan your week with the Upcoming view; Use the list, board, calendar and table layouts; Find anything with search.
  - **Goals, seasons & rituals:** Introduction to goals; Plan a season; Track progress with milestones and goal status; Introduction to rituals; Sort timeless tasks into Now, Next and Later.
  - **Coach:** Introduction to the Coach; Connect an AI provider; Review the Coach's drafts; Manage what the Coach has learned.
  - **Integrations:** Use Google Calendar with Todalo; Troubleshoot Google Calendar.
  - **Apps & account:** Use keyboard shortcuts; Change your theme and sounds; Manage your account; Sync and working offline; Allow notifications and the microphone on Mac; Troubleshoot sign-in; What's new.
- Time blocking is covered inside the Today article and Filter Assist inside the filters article. Neither has its own page.
- Ramble sits under Tasks & capture: it is phrase spotting, not an AI feature (ADR 0003), and it stages tasks until the user confirms (ADR 0005).

### Content model

- One MDX file per article. Each article declares: title, description (also used as the meta description and search excerpt), category, order within the category, platforms it applies to, related articles, an optional badge (`experiment`), and a published flag.
- Categories are declared once in a single list with name, slug, tagline, order and card illustration.
- A category is shown on the landing page and in navigation only when it has at least one published article. Unpublished articles are not built, not linked, not indexed and not in the sitemap.
- All reads of content go through one content module that returns published categories and articles. Pages, navigation, search, the sitemap and related-article lists consume that module and never read files directly.
- "Last updated" shows the author's first name and the date of the article file's last commit. The author is Devin for all v1 articles.

### Landing and category pages

- Landing: heading, bonsai hero illustration, search box, four suggested-search chips ("Add a task", "Recurring dates", "Connect the Coach", "Google Calendar") that open pre-filled searches, the grid of category cards, then "Still need a hand?" with the support address.
- No "Learn and explore" row, no popular-articles list.
- Category page: category title and tagline, all its articles on one page as title cards, a way to switch category, and "Couldn't find what you need?" with the support address.

### Article template

- Breadcrumbs; title; a two-to-four sentence intro with no heading; body; closing "Get in touch" section.
- Sidebar: platforms, table of contents built from second-level headings with position tracking, related articles (up to four), last updated. On small screens the table of contents moves into a collapsible control.
- Body components available to authors: numbered steps, Tip / Note / Warning callouts, tables, a themed screenshot, a platform-specific block, and a keyboard-key component that renders the right modifier for the chosen platform.
- "Get in touch" gives the support address `support@todalo.app` and a control that opens the existing FeatureSpace feedback board for Todalo. How that widget embeds outside the client must be confirmed; the fallback is a plain link to the board.
- No "Was this helpful?" vote, no comments, no reading time, no video in v1.

### Platform switcher

- One global platform choice, Web or Mac, stored in the browser and applied on every page.
- The default on first visit is Mac when the browser reports macOS, otherwise Web.
- The switcher control is rendered only in articles that contain at least one platform-specific block. Content outside such blocks is written once for all platforms.
- Platform-specific blocks for the platform not chosen are present in the page source but hidden, so search engines and in-page search still see them.
- The keyboard-key component follows the same choice: Mac keys for Mac, Ctrl-style keys for Web on non-Apple systems, Mac keys for Web on macOS.

### Theme

- Light and dark themes. The default follows the visitor's system setting; an explicit choice is remembered. (The app itself never follows the system setting; the help center deliberately differs because visitors arrive without an app preference.)
- Light theme uses the landing page's paper background with ink text and Todalo red as the single accent. Dark theme uses the badge's dark paper and light ink values with the same red.

### Illustrations

- Higgsfield generates nine images: the landing hero, seven category cards and one shared social-preview image.
- A style trial comes first: the "Get started" card is generated in five candidate styles and the author picks one.
  1. Sliced 3D: the object is built from stacked horizontal slats like the bonsai mark, matte paper-white, one red slice.
  2. Sliced ink: the same slat construction as flat black strokes on paper.
  3. Sliced glass: slats in translucent red glass with soft shadows.
  4. Paper-cut relief: layered cut paper, ink and red.
  5. Isometric line: thin ink outlines with a red fill on one element.
- Each candidate is judged with its background removed on both the light and the dark page background. A style that reads on only one background is rejected. Two versions per card are produced only if no style passes.
- The chosen trial image becomes the style reference for every later generation. The prompt wording, palette values, reference image, model and settings are recorded in an illustration style guide in the repository so that future images match.
- Each category card shows a different object in the chosen style. The bonsai is reserved for the landing hero and the social-preview image. Starting subjects, open to change during generation: seedling (Get started), task card (Tasks & capture), shelves (Organise & views), mountain path (Goals, seasons & rituals), the Coach blob (Coach), plug (Integrations), laptop (Apps & account).
- Illustrations contain no people, no faces and no text.
- Illustrations appear only on the landing and category pages. Articles never contain generated images.

### Screenshots

- In-article visuals are real screenshots of the new client: tightly cropped to the relevant fragment, never a full window, placed on a paper-coloured rounded backdrop.
- A capture script drives the web build of the client signed in to the seeded demo account, at a fixed size, and saves each shot in light and dark. The themed screenshot component shows the one matching the page theme.
- The demo account's seed data is the sample data shown in screenshots, so it must read as realistic tasks, projects and goals.
- Mac-only interface (title bar, permission prompts, system notifications) is captured by hand in both themes.
- Images are sparse by design: an article gets a screenshot only where the text alone would leave the reader unsure where to click.

### Writing style

- Second person, present tense, plain and calm, matching the tone of the app's copy. Contractions are fine.
- Titles are sentence case and follow fixed patterns: "Introduction to X" for concepts, a verb-first title for how-tos, "Troubleshoot X" for fixes.
- Second-level headings start with a verb. Steps are imperative, one action each, with location cues ("at the top right"). "Click" is used for Web and Mac; "Tap" is reserved for iOS.
- Interface labels are bold and spelled exactly as in the client.
- How-to articles run roughly 400 to 1,000 words; introductions and references may be longer.
- These rules are recorded in a writing style guide in the repository.

### Search, indexing and analytics

- Full-text search over published articles using the framework's built-in static index, with no external search service. Results show category and excerpt.
- All published pages are public and indexable. The site emits a sitemap, a robots file, per-page titles and descriptions, and one shared social-preview image.
- Page views and search queries are sent to the existing PostHog project used by the marketing site, tagged so help traffic can be separated from landing traffic.

### Changes outside the docs application

- In the client, "Help & resources" opens the help center in the browser (the system browser on Mac). The keyboard-shortcut sheet stays reachable by its own shortcut and menu entry.
- In-app strings that promise a help link point to the matching article once it is published.
- The privacy and terms pages replace the personal contact address with `support@todalo.app`.

### Process

- Articles are drafted by an agent from the client code, the domain glossary and the ADRs, then reviewed by the author one category at a time. An article is published only after review.
- Launch order: style trial; docs application with landing, template, search, both themes and the "Get started" category; then the remaining categories in the order listed above, each going live when reviewed.
- "What's new" is written from the client's existing release notes data, not maintained as a second copy by hand.

## Testing Decisions

- A good test here checks what a visitor or the author can observe (which articles and categories are published, whether links resolve, which platform content shows) and not how the framework renders pages.
- **One primary seam: the content module.** Tests load the real content through it and assert:
  - every published article has the required details and belongs to a declared category;
  - a category with no published articles is absent from the published list;
  - unpublished articles are absent from the published list, navigation data, search data and sitemap data;
  - every internal link, related-article reference and image reference in a published article resolves, and every screenshot exists in both themes;
  - every slug is unique and matches the address pattern.
  These run as part of the normal test command, so a broken article fails the build.
- **Platform choice logic** is tested as pure functions: default from the reported operating system, stored choice overriding the default, whether an article needs the switcher, and which modifier keys are shown for each platform and operating system.
- No tests are written for page rendering, the framework's search, illustrations or screenshot output. Those are reviewed by eye during category review.
- Prior art: the repository's Vitest unit tests of pure modules in the marketing application's library folder (pricing, quick-add parsing, task URLs) and in the shared packages. The new tests follow the same style and run under the same root test command.

## Out of Scope

- Billing, plans and subscription articles. Billing does not exist in the app.
- Collaboration, Reporting and other inert or excluded features.
- The member badge and "Founding member" pill.
- Documentation of the legacy Next application.
- iOS and Android content, until those apps ship.
- Languages other than English.
- Video, GIFs and animated clips.
- A "Was this helpful?" vote, comments, and a contact form.
- Developer or API documentation.
- A CMS or any editing interface; content is edited as files.
- Extracting a shared UI package from the client.
- Setting up the `support@todalo.app` mailbox and the `help.todalo.app` DNS record. Both are done by the owner.

## Further Notes

- Reference for structure and tone: the Todoist Help Center. Its articles are text-first; four of ten sampled articles had no image, and illustrations appear only on hub pages. The plan follows that split.
- The app's theme tokens are marked provisional and the logo is noted as a placeholder in the landing brief. The illustration style guide should name the palette values it used, so the set can be regenerated if the brand changes.
- The style trial spends Higgsfield credits on five images, and the full set on roughly nine more plus retries.
- Two facts to confirm before building: framework support for the repository's Next version, and how the FeatureSpace widget embeds outside the client.
- The web version of the new client is not yet in production. Until cutover, web visitors may read help that is slightly ahead of what they see.
- The root README still calls the product by an old name and the marketing application still carries default page metadata; neither is part of this work, but both are visible to anyone arriving from the help center.
