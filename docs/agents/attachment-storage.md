# Personal attachment storage

Project file paste creates one task per file, named after the file, and persists its bytes in `task_attachments.content` as base64 text in the existing PostgreSQL database. Ordinary task lists and attachment metadata endpoints do not select content. Task/account deletion cascades to attachment rows. No additional provider, credentials, filesystem volume or browser storage is required.

Deploy the generated `0009_faithful_weapon_omega.sql` migration after `0008_funny_plazm.sql` using the project's normal database deployment process. This feature does not run migrations automatically. Include `task_attachments` in database backups; base64 content occupies about one third more space than the original bytes. Monitor database storage and endpoint traffic for production capacity. Neon HTTP batch executes the task and attachment inserts in one transaction.

Uploads require a signed-in session, exact same-origin request and owned project. Downloads and metadata require attachment/task/account ownership and, when the task has a project, project ownership. Attachments remain downloadable after a task moves to Inbox. File limits: 5 files per paste, 5 MiB per file, 10 MiB total; the body reader rejects over-limit multipart requests before parsing. Empty files, invalid MIME metadata, path/control-character names and names longer than 255 characters are rejected. Types are treated as untrusted metadata. Downloads use `application/octet-stream`, attachment disposition, sanitized ASCII fallback and encoded Unicode name, `nosniff`, a sandbox CSP and private/no-store caching; content is never rendered inline.

Default Command/Control+V relies on native clipboard `paste` file data and leaves the key event available to the browser. Only active-project paste events (including default body focus after navigation) outside text editors, dialogs and IME composition create tasks. Text-only paste remains native. Disabled or overridden native bindings do not create tasks through native file paste. Custom bindings request the browser Clipboard API in the key gesture and require secure-context/browser permission support. Browsers commonly expose images only, omit original filenames or reject file reads; UI errors explain restoring the default and retrying. Images without names get a `Pasted image N.png` or `.jpg` name. Clipboard-read limitations cannot be eliminated by a web shortcut.

Failed uploads leave the original files available for retry in the project view. If a network interruption hides a successful response, check the project before retrying to avoid duplicate tasks. No clipboard contents are persisted before the authenticated upload succeeds. Tests cover the upload/list/download public endpoints with the database and session as external boundaries, plus native/custom paste, composition, overrides, permission failures and an end-to-end paste-to-download path. Native OS clipboard capture still requires manual browser verification.
